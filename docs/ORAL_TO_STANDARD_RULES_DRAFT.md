# 口语转标准文本规则草案

状态：当前默认规则草案，供人工继续修改。本文件中的短版默认规则已同步到设置页“整理文本规则”、服务端默认配置和 `CodexVoicePromptBridge` 的兜底默认规则。

## 资料依据

- Speechpad 的转写说明把逐字稿和干净稿区分开：干净稿会移除 filler words、false starts 和重复词，用于更重视可读性的场景；法律、保险等需要完整语气证据的场景则应保留逐字内容。参考：https://www.speechpad.com/transcription/verbatim
- GoTranscript 对 clean verbatim 的边界描述是：去掉低价值噪声，同时保留讲述者的声音、措辞和意义；不要把事实、语气或语法改到改变含义。参考：https://gotranscript.com/en/blog/clean-verbatim-vs-verbatim-oral-history
- NARA Plain Language 原则强调：先说重点，一段只放一个想法，用主动语态、短句、日常词，删除不必要的词，用标题和列表帮助阅读。参考：https://www.archives.gov/open/plain-writing/10-principles.html
- Microsoft Style Guide 建议使用更大的意思和更少的词，弱句式要改成以动作开头的表达。参考：https://learn.microsoft.com/en-us/style-guide/top-10-tips-style-voice
- ASR spoken-to-written 研究通常把口语转书面拆成标点、文本规范化、大小写和 disfluency 处理等任务；中文没有大小写，但仍需要标点、数字/术语规范和犹豫修复。参考：https://arxiv.org/abs/2210.15063
- `GB/T 15834-2011 标点符号用法` 是现行中文标点国家标准，适合作为中文断句和标点的底线依据。参考：https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=22EA6D162E4110E752259661E1A0D0A8&refer=outter
- 中文技术写作应优先保证准确、清晰、简洁；中英文混排、术语、数字和标点要稳定一致。参考：https://github.com/RightCapitalHQ/chinese-style-guide

## 核心目标

把用户语音识别出的中文口述，整理成可以直接发给 Codex 的标准文本。默认目标不是文学润色，也不是法律逐字稿，而是“保留真实意图的干净提示词”。

输出应满足：

1. 准确：不改变事实、否定、条件、时间、数字、路径、文件名、专有名词和用户真实取舍。
2. 清楚：先表达主任务，再列补充要求、限制条件和验证要求。
3. 简洁：去掉不承载意义的口头禅、重复句、犹豫词和绕路表达。
4. 可执行：让 Codex 能直接知道要检查什么、修改什么、验证什么、暂时不要做什么。
5. 可回退：遇到关键歧义时保留“需确认”，不要编造用户没有说过的决定。

## 默认处理流程

1. 识别意图：先判断这段话是在提需求、补充限制、修改前一条指令、表达疑问，还是要求暂缓。
2. 固定事实：先保护路径、命令、文件名、网址、数字、日期、版本号、专有名词、否定词和条件词。
3. 去噪：删除不影响含义的“嗯、呃、啊、这个、那个、就是、然后、对吧、是吧、好吧、什么的、之类的”等口头填充。
4. 合并重复：同一意思重复出现时只保留一次；如果第二次补充了新限制，把新限制合并进去。
5. 修复自我纠正：出现“不是 A，是 B”“不对，改成 B”“前面那个不要，按后面这个”时，以后面的明确修正为准。
6. 重组句子：把口语长句切成短句；一件事用一段，多件事用编号列表。
7. 标准化表达：把“你能不能”“是不是可以”“我想让你”转成直接任务，但保留真正的可行性询问。
8. 添加执行边界：如果用户说“先别实现”“我先看看”“等我改完”，输出中必须明确“暂不修改程序”或“先给草案”。
9. 形成交付要求：编码类请求默认补上“检查现状、实施修改、最小验证、说明结果”的顺序，除非用户明确只要分析。
10. 最后自检：检查是否误删否定词、是否引入新事实、是否把疑问改成命令、是否过度压缩导致边界丢失。

## 可删内容

以下内容只有在不承载含义时才删除：

- 犹豫词：嗯、呃、额、啊。
- 填充词：这个、那个、就是、然后、那么、好的、好。
- 语气确认：对吧、是吧、好吧、你知道吧。
- 模糊尾巴：什么的、之类的、等等。
- 单纯重复：连续重复的词、短语或整句。

不要删除：

- 否定：不、不要、不能、别、不是、暂时不要。
- 顺序：先、再、然后、最后、之前、以后、下一步。
- 条件：如果、除非、只有、否则、前提是。
- 程度：必须、尽量、至少、优先、默认、只、全部。
- 态度和取舍：我不满意、我先修改、我再确认、不要提交。

## 结构化规则

一段口述中出现下列信号时，优先输出编号列表：

- “第一件事、第二件事、另一个事情、还有、另外、然后我还想”
- “一是、二是、三是”
- “先……再……最后……”
- 同一段中有两个以上动作动词，例如“加、查、整理、落实、验证、提交”

列表项格式建议：

```text
请继续处理：

1. 在 README 中增加一段可复制给 Codex 的安装提示词，说明克隆、构建、启动校准中心和默认安全开关。
2. 联网查找口语转标准文本的规则依据，整理一份可执行规则草案，先供我修改。
3. 暂时不要把新规则写入程序；等我确认草案后再实现、验证并提交。
```

## 语气和措辞

- 默认使用简体中文。
- 默认使用直接、礼貌、可执行的表达。
- 不自动添加“请执行：”“请根据以下口述内容理解我的需求”这类固定标题。
- 保留用户明确指定的称呼、产品名、路径、命令和代码。
- 技术词保持常用写法，例如 Codex、GitHub、PowerShell、README、JSON、API、LLM、token。
- 中英文混排时，中文和英文/数字之间保留空格；中文标点使用全角，代码、命令、路径内的标点保持原样。

## 疑问和歧义

需要保留为问题的情况：

- 用户本来就在问“能不能”“是不是应该”“有没有更好方案”。
- 用户明确要求先评估、先检查、先给方案。
- 原文存在关键缺失，例如没有仓库地址、没有目标文件、没有许可证选择。

可转为命令的情况：

- “你能不能去查一下”转为“请联网查找并整理”。
- “是不是还应该做检查”转为“请补充发布前检查”。
- “你应该都要去检查去做的”转为“请检查并补齐这些发布惯例”。

## 推荐短版默认规则

这段是设置页“整理文本规则”和整理器兜底逻辑当前使用的默认值：

```text
先判断原始口述的真实意图和任务边界；保留事实、否定、时间、数字、路径、文件名、专有名词和条件，不新增原文没有的信息。删除不承载意义的口头禅、重复句、犹豫词和自我打断；对“不是 A，是 B”“不对，改成 B”以后者为准。将“你能不能/是不是可以”改为直接可执行请求，但真正的可行性询问要保留为问题。多件事按 1、2、3 拆分，每项写成“动作 + 对象 + 验证/交付要求”。长句按意图断句，使用规范中文标点；保留必要的语气和不确定性，关键歧义标为“需确认”。输出应简洁、清楚、可执行，适合直接发给 Codex；不要额外添加固定标题。
```

## 需要你确认的取舍

1. 输出要更像“正式任务指令”，还是保留更多你的自然口吻？
2. 多件事时是否固定输出编号列表？
3. 对“你能不能、是不是可以”这类句子，默认改成命令，还是更多保留为问题？
4. 是否允许工具在明显编码任务中自动补充“验证并说明结果”？
5. 如果一句话里重复了同一要求，是否默认只保留最后一次更完整版本？
