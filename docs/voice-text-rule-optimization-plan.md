# 语音转文字整理规则优化方案

## 1. 背景

当前语音输入链路已经可以读取 Codex 本地语音历史或剪贴板文本，并通过本地整理器做繁转简、口头禅清理、术语纠正、提示词化和简单结构化。但用户近期反馈了两个核心问题：

1. 口头禅仍然残留较多，尤其是自然口语里的拖泥带水表达，不总是能被现有固定正则覆盖。
2. 分条判断不稳定：该分成 1、2、3 条时不一定分；不该分时，句子中间的数字、日期、端口、版本号等又可能诱发错误分条。

这说明当前整理器的问题不只是“规则少”，而是缺少一个独立的结构判断阶段。现有实现更像按顺序执行正则替换，默认整理规则里长期包含“拆分、总结、1、2、3、要点”等触发词，导致 `ShouldPreferStructuredPrompt` 容易过度倾向结构化。

## 2. 目标

本方案的目标不是继续堆更多单点正则，而是把整理流程升级为“先判断，再整理”：

```text
原始转写
-> 数字/路径/术语保护
-> 口语噪声清理
-> 意图结构判断
-> 分条决策
-> 文本润色
-> 输出校验
```

优化后应满足：

- 默认更保守：不确定是否应该分条时，不自动分条。
- 数字更安全：日期、路径、版本号、端口、金额、时间、百分比、快捷键等不被误判为列表编号。
- 口头禅清理更稳：清掉无语义连接块，但保留真正承载语义的词。
- 结构化更有依据：只有明确出现枚举意图或多个独立任务时，才输出 1、2、3。
- 长期可维护：用户明确提出的稳定偏好进入长期规则；临时表达、单次抱怨、强个人上下文不进入永久规则。

## 3. 当前问题定位

### 3.1 分条触发过宽

当前 `ShouldPreferStructuredPrompt` 会根据整理规则中的“整体意图、重组、拆分、总结、要点、压缩、token、提示词、高效、一二三”等词触发结构化。由于默认整理规则总是包含这些词，整理器倾向于对较多文本尝试分条。

风险：

- 口述中的普通数字被误识别为列表编号。
- 原本是一段解释性背景，被拆成任务列表。
- 用户只是提到“1 秒、3 个文件、A3-v3、127.0.0.1”，结果被错误结构化。

### 3.2 分条缺少置信度

当前逻辑主要看固定表达，例如“第一、第二、另外、还有、下一步”等。它没有明确区分：

- 枚举编号：第一、第二、第三。
- 事实数字：3 秒、500ms、2026-05-27。
- 数量描述：有 3 个文件、10 到 20 条样本。
- 版本或标识：A3-v3、net10.0、127.0.0.1:8793。

### 3.3 口头禅清理粒度偏粗

当前 `RemoveSpeechFillers` 和 `CleanPromptItem` 会删除部分“嗯、呃、啊、那个、这个、就是、然后”等，但真实口述里常见的是组合块：

- “然后的话”
- “就是说”
- “怎么说呢”
- “你知道吧”
- “反正就是”
- “这个这个”
- “就是那个意思”

简单删单词容易漏删，也可能误删承载语义的“就是”，例如“这个问题就是路径不对”里的“就是”更接近判断连接词，不应该粗暴删除。

## 4. 设计原则

1. 保守优先：整理器宁可少分条，也不要错误分条。
2. 保护优先：先保护数字、路径、文件名、专有名词，再做结构判断。
3. 判断与生成分离：先生成结构决策，再决定如何输出文本。
4. 本地优先：短期方案只使用本地规则，不新增云 API。
5. 可回滚：输出校验发现误伤时，能回退到普通段落。
6. 长期规则要稳定：只有跨场景有效、符合项目边界的规则才进入长期规则。

## 5. 初步技术方案

### 5.1 增加保护跨度识别

新增 `ProtectLiteralSpans` 或等价逻辑，在分条前识别并临时保护：

- 日期：`2026-05-27`、`5 月 27 日`
- 时间和时长：`3 秒`、`500ms`、`2 分钟`
- 端口和地址：`127.0.0.1:8793`、`localhost:3000`
- 版本和型号：`A3-v3`、`net10.0`、`v0.1.0`
- 路径和文件名：`docs/development-handbook.md`、`Program.cs`
- 快捷键：`Ctrl+V`、`Ctrl+Alt+D`
- 金额、百分比、容量：`20 MB`、`30%`
- 数量范围：`10 到 20 条`

保护方式可以是内部占位符，也可以只在判断阶段跳过这些 span。最终输出必须恢复原文。

### 5.2 增加结构决策对象

在 `ApplyRuleDrivenPromptStructure` 前增加一个内部决策结果：

```json
{
  "mode": "single_request | multi_request | explanation | question | mixed",
  "shouldList": false,
  "confidence": 0.0,
  "reasons": [],
  "protectedSpanCount": 0
}
```

短期可以不真的输出 JSON，只在代码里用类型或局部变量表达。重点是让分条行为由 `shouldList + confidence` 决定，而不是只由默认 rewrite rule 中的关键词决定。

### 5.3 明确分条触发条件

只有满足以下至少一类条件时才允许分条：

- 明确枚举词：`第一/第二/第三`、`第一个/第二个/第三个`、`首先/其次/最后`。
- 明确数量意图：`有三件事`、`分成三点`、`有几个点`、`分别是`。
- 多个独立动作：同一段内有两个以上独立命令动词，且由 `另外/还有/同时/下一步/最后` 连接。
- 用户明确要求结构化：`列成 1、2、3`、`按步骤`、`分条`、`拆成要点`。

以下情况不应单独触发分条：

- 普通数字、日期、端口、版本号。
- “一下、一个、一点、第二天、三秒钟”等非枚举表达。
- 默认整理规则里出现“拆分、总结、要点”但原文没有明确多任务信号。

### 5.4 增加输出校验器

新增 `ValidateStructuredOutput` 或类似逻辑：

1. 如果输出被分成列表，但原文没有明确枚举信号，且列表项少于 2 个独立动作，回退为普通段落。
2. 如果列表编号附近只出现受保护数字，判定为误分条并回退。
3. 如果列表项是碎片化短句，例如每项少于 6 个汉字且没有动作动词，回退为普通段落。
4. 如果原文含有路径、端口、版本号，校验输出中这些内容完整保留。

### 5.5 口头禅清理升级为块级清理

保留现有单词清理，同时增加“无语义连接块”清理：

- `然后的话`
- `就是说`
- `怎么说呢`
- `你知道吧`
- `反正就是`
- `大概就是说`
- `这个这个`
- `那个那个`
- `嗯然后`

但要增加保护条件：当这些词处于事实判断、定义、转折或引用结构中时不删除。例如：

- “问题就是路径不对。”
- “这个变量就是 userId。”
- “也就是说，它不是后台直写。”

### 5.6 增加整理模式

建议后续在配置里增加两个模式：

- `conservative`：默认模式。清理口头禅、纠错、标点整理；只有高置信度才分条。
- `structured`：强整理模式。更主动总结、分条、压缩上下文。

当前项目默认应使用 `conservative`，避免误伤。

### 5.7 可选结构规划器

中期可以增加一个可选结构规划器，只负责判断，不直接重写全文：

```json
{
  "shouldRewrite": true,
  "shouldList": false,
  "cleanupLevel": "moderate",
  "preserve": ["A3-v3", "3 秒", "PROJECT-STATUS.md"]
}
```

规划器可以先是本地规则，后续再可选接本地小模型或云端 LLM。即便接入模型，也不建议让模型直接改写全文，避免丢失关键约束、隐私不可控和输出漂移。

## 6. 用户规则长期化判断

| 编号 | 用户提出或隐含的规则 | 是否进入长期规则 | 判断 |
| --- | --- | --- | --- |
| VR-001 | 口头禅要更彻底清理 | 是 | 这是跨场景稳定需求，符合项目目标。应长期进入口语噪声清理规则。 |
| VR-002 | 该分成 1、2、3 时要分 | 是 | 应进入长期规则，但必须通过结构决策和置信度控制，不能无条件分条。 |

| VR-005 | 默认更像 AI 提示词，清楚可执行 | 是 | 已是当前项目核心目标，应保留，但不能以牺牲事实和数字为代价。 |
| VR-006 | 保留事实、否定、时间、数字、路径、文件名、专有名词 | 是 | 已在默认规则中，应继续强化到校验器。 |

| VR-010 | 继续靠用户逐条校准生成替换规则 | 否，不能作为主路线 | 可作为补充，但不能成为解决结构判断问题的主要办法。 |

## 7. 推荐实施顺序

### 阶段 1：保守结构规划

目标：先解决误分条和数字误伤。

改动点：

- 新增数字/路径/版本号保护判断。
- 修改 `ShouldPreferStructuredPrompt`，默认规则中的“拆分/要点/提示词”不再单独触发分条。
- 修改 `ExtractPromptItems`，只在明确枚举或多任务信号下提取列表项。
- 增加输出校验，误分条时回退普通段落。

验证样例：

- “这个服务在 127.0.0.1:8793 上，等 3 秒再检查。”不应分条。
- “我有三件事，第一检查配置，第二更新文档，第三跑验证。”应分三条。
- “你帮我看一下 A3-v3 的声音，语速 +7%，音高 -1Hz。”不应按数字分条。

### 阶段 2：块级口头禅清理

目标：减少自然口语残留，同时不误删承载语义的词。

改动点：

- 增加无语义连接块词表。
- 对“就是、然后、这个、那个”增加上下文保护。
- 增加口头禅清理前后对照测试。

验证样例：

- “然后的话你帮我看一下这个项目。”应变为“请检查这个项目。”
- “问题就是路径不对。”应保留判断关系。
- “也就是说，它不是后台直写。”应保留“也就是说”的解释关系或改为“换言之”。

### 阶段 3：整理模式配置

目标：让用户能在“保守”和“强整理”之间选择。

改动点：

- 在配置里加入 `rewriteMode`，默认 `conservative`。
- 网页设置页增加模式选择。
- 命令行支持 `--rewrite-mode conservative|structured`。

### 阶段 4：可选结构规划器

目标：当规则判断仍不够时，增加可插拔的规划层。

先实现本地规则版规划器；只有用户明确接受后，再评估本地小模型或云端 LLM。规划器只输出结构决策，不直接改写全文。

## 10. 当前结论

最值得优先实施的是“阶段 1：保守结构规划”。它解决的是整理器的判断机制问题，不依赖用户每次手动校准，也不引入云端 API。阶段 1 做完后，再补“阶段 2：块级口头禅清理”。这两步完成后，语音转文字的稳定性会比继续堆单条替换规则更明显。
