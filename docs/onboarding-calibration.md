# Topic-Based Onboarding Calibration

本文记录“安装期话题式自由口述校准”的设计草案。

## 目标

首次配置中介时，不要求用户照读固定文本，而是给用户几个固定话题，让用户按自己的真实说话习惯自由表达。话题要先从轻松、宽泛、低压力的日常聊天开始，再逐步进入日常规划、任务指令、工作流程思考、整理偏好和项目词汇。中介根据这些样本了解用户在不同认知负荷下的语言习惯，再生成个人化的文本整理规则。

可学习的内容：

- 用户常见口头禅，例如“嗯”“那个”“就是”“然后另外”。
- 用户自然聊天的开场、停顿和转折方式。
- 用户在不同话题难度下的表达差异：轻松聊天通常语速更快、停顿更少；工作思考通常会出现更多卡顿、修正和补充。
- 用户组织需求的方式，例如先铺垫、再说目标、最后补充限制。
- 用户常见任务表达，例如“给我一个”应改成“给出一个”。
- 常见识别误差，例如 `cofirects` 应统一为 `Codex`，`wisper` 应统一为 `Whisper`。
- 项目词表和专有名词，例如 `Codex`、`TypeWhisper`、`Whisper`。
- 用户希望保留、不希望被擅自改写的表达。
- 用户希望如何压缩口述内容：总结要点、减少上下文、节省 token，并保留关键约束。

## 当前技术边界

当前主链路使用 Codex 自带语音识别。本项目无法直接训练或修正 Codex 底层声学模型，也无法保证拿到原始音频样本。

因此第一阶段校准只做文本层适配：

```text
用户围绕固定话题自由口述 -> Codex 输出原始识别文本 -> 中介分析语言习惯 -> 生成个人词表/口头禅/替换规则 -> 后续整理时使用
```

这比固定朗读更适合当前目标，因为我们真正要优化的是“用户自然说话后，文本怎样被整理成更好的提示词”。

需要注意：如果 Codex 只给最终文本，不提供音频或时间戳，本项目不能准确测量真实语速和停顿时长，只能通过文本里的口头禅、重复、断句、标点和自我修正痕迹做近似判断。未来如果 Codex 提供时间戳、音频或识别事件，再把真实语速和停顿统计加入校准。

## 分层采集模型

不要把用户压成一种统一的“语音习惯”。同一个人在不同认知负荷下会表现出不同说话方式，所以配置按层采集：

1. 轻松聊天层：天气、吃饭、今天状态。目标是采集自然开场、低思考负担下的基线表达。
2. 日常规划层：今天计划、自我介绍、平时怎么使用 Codex。目标是采集轻度组织语言、排序和回忆时的表达。
3. 工作任务层：任务指令、问题反馈、整理偏好、项目词汇。目标是采集给 Codex 下指令和描述问题时的表达。
4. 思考推理层：工作流程、方案取舍、抽象判断。目标是采集用户边想边说时的卡顿、转折、修正和补充方式。

后续生成个人规则时，也应该保留“场景”信息。例如“嗯”在轻松聊天里可以少处理，但在工作思考里可能只是组织语言的停顿，不一定全部删除；“然后另外”在任务指令里常常意味着需要拆成新句。

## 安装期流程草案

1. 先显示 2 个轻松聊天话题，例如天气状态、最喜欢的食物。
2. 再显示 1 到 2 个日常规划话题，例如今天计划、简单自我介绍。
3. 再显示 2 到 3 个工作相关话题，例如任务指令、问题反馈、整理偏好。
4. 最后显示 1 到 2 个高思考负荷话题，例如工作流程思考、方案取舍。
5. 每个话题要求用户自然说 30 到 60 秒。
6. 每段说完后，让用户把 Codex 原始识别文本交给中介。
7. 中介输出“原始识别 / 整理结果 / 发现的语言习惯 / 建议规则 / 适用场景”。
8. 用户确认哪些规则应该保留，哪些不要自动改。
9. 生成本地个人配置，例如 `config/voice-habit-profile.json`。
10. 后续 `CodexVoicePromptBridge` 读取该配置，优先应用个人规则，再应用通用规则。

## 持续学习闭环

安装期校准只能建立第一版语言习惯，后续还需要从真实使用中继续校准。当前建议把持续学习限定在语音审核链路内：

```text
Codex 原始识别文本 -> 中介自动整理文本 -> 用户在审核页确认的最终文本 -> 本地差异记录 -> 每日候选规则
```

边界：

1. 固定配置入口地址是 `http://127.0.0.1:8793/`，作为访问与启动偏好保存；“随 Codex 启动”表示启动 Codex 时自动启动本地校准服务并打开固定配置网页。真正注册启动任务需要用户确认后执行。
2. 自动对比校准默认关闭，用户需要在“持续学习”中主动开启。
3. 持续学习、自动对比差异记录和每日自动迭代时间属于同一个功能组；持续学习开启后才配置每日时间。
4. 自动对比校准只在 `web/review-panel.html` 点击“保存选择”或用户主动保存校准样本时记录。
5. 主动校准在同一个网页里进行：用户选择话题后，可靠流程是点击“开始校正”，页面从 Codex 本地语音历史导入原始识别文本，并自动生成整理文本；原始识别文本只读，“发送给 Codex 的最终文本”可由用户修改。Codex 当前没有向本地网页暴露稳定的输入框草稿读取接口，Computer Use 也不是可嵌入网页的产品 API，因此自动流程不做后台监听，只是用户点击后的前台尝试。页面不能拦截 Codex 的发送按钮，但可在回填后一段时间内轮询 Codex 本地会话 JSONL，发现相似的新增用户消息后，把真正进入对话的文本同步回本页并自动保存样本。校准样本以本页“发送给 Codex 的最终文本”为准；如果旁路确认未命中，回填后又在 Codex 输入框里修改，保存样本前需要同步回本页。录入等待期间不要切换对话、跳转页面或移动焦点；如果语音窗口一直显示等待，先停在当前对话，避免语音结果失效。用户修改这段最终文本后，点击“保存样本”只保存本地样本，点击“更新规则”才生成本地候选规则。默认整理规则会把口述压缩成更短、更省 token、更符合 AI 提示词工程的指令。
6. 记录内容限于当前语音审核链路里的原始识别、自动整理、发送给 Codex 的最终文本和用户主动填写的整理规则。
7. 不监听键盘、鼠标、全局剪贴板或普通手打输入，也不把语音校准记录挪作其他用途。
8. 每日迭代只生成候选规则，进入永久规则前需要人工审核。

这样可以把用户最后确认的文本当作“标准答案”，但不越界监控用户在 Codex 里的其他操作。

## 话题配置

初始话题放在：

```text
.\config\onboarding-topic-prompts.json
```

当前建议话题：

- 天气和状态：学习低思考负担下的自然开场、语气和低口头禅状态。
- 最喜欢的食物：学习轻松偏好表达、口感味道描述和舒适区词汇。
- 今天的计划：学习轻度规划、排序和任务分组表达。
- 简单自我介绍：学习用户介绍自己或介绍使用习惯时的表达。
- 问题反馈：学习用户如何描述不符合预期的识别结果。
- 任务指令：学习用户如何给 Codex 下多步骤任务。
- 工作流程思考：学习用户边想边说时的停顿、修正和转折。
- 取舍和判断：学习用户做抽象判断和权衡时的句子结构。
- 整理偏好：学习哪些口头禅要删、哪些表达要保留。
- 项目词汇：学习工具名、插件名、热键名和易错词。

## 个人配置草案

未来生成的 `config/voice-habit-profile.json` 可以采用类似结构：

```json
{
  "version": 1,
  "contextProfiles": {
    "low_load_casual": {
      "fillerWords": ["嗯", "啊"],
      "rewriteStrength": "light"
    },
    "work_task_expression": {
      "fillerWords": ["嗯", "呃", "那个", "就是", "然后另外"],
      "rewriteStrength": "normal"
    },
    "high_load_reasoning": {
      "fillerWords": ["嗯", "呃", "就是"],
      "rewriteStrength": "careful"
    }
  },
  "literalReplacements": {
    "cofirects": "Codex",
    "wisper": "Whisper",
    "配件": "插件"
  },
  "phraseReplacements": {
    "我希望你能": "请",
    "给我一个": "给出一个"
  },
  "protectedTerms": ["Codex", "TypeWhisper", "Whisper"],
  "doNotRewrite": ["用户明确要求原样保留的短语"]
}
```

这个配置不应上传，不应记录大量历史转写内容，也不应包含账号、项目秘密或私人敏感文本。
